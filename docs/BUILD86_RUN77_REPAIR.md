## Run81 periodic-timeline correction

Run81 (`bddf8d390ca7cd63077f382059271f45e1faf69e`) disproved the assumption that restoring the run74 dependency-install ordering alone would make the first MP3 remote checkpoint reliable. The simulator application still built, synchronization completed and the run produced all 54 required UI records, but online playback again failed when one `getPosition` request exceeded the unchanged 3000 ms guard. Offline remained blocked by that failed prerequisite and Archive/IPA correctly did not run.

The remaining blocking path is source-confirmed. RNTrackPlayer's exported `getPosition` returns `QueuedAudioPlayer.currentTime`; SwiftAudioEx 0.14.7 implements that property with a synchronous `AVPlayer.currentTime()` call. The same SwiftAudio wrapper already receives real playback CMTime from `AVPlayer.addPeriodicTimeObserver`. This correction caches that AVPlayer-produced periodic CMTime inside `AVPlayerWrapper` under an `NSLock`, makes `currentTime` a nonblocking cache read, updates the cache immediately on explicit seek, resets it during reset and at the exact `replaceCurrentItem` point, then advances it only from AVPlayer's periodic callback. This keeps all callers on one real media timeline instead of inventing JavaScript progress or widening the test timeout.

The post-install patch is strict and runs after the existing SwiftAudio seek patch. If the pinned wrapper anchors change, CocoaPods installation fails instead of silently shipping the synchronous getter. The source regression verifies the pinned current-time, seek, reset, item-replacement and periodic-callback anchors, idempotency, rejection of unknown/duplicated source, and confirms the playback smoke test still bounds `getPosition` at 3000 ms and still requires more than 0.25 seconds of observed advancement. Native behavior remains gated by the next Actions run; this source check is not treated as simulator, offline, Archive or IPA evidence.

## Run82 compile correction

Run82 (`e75576d9cf03c98f9d781f1e64c252eee7796f4e`) did not reach the native playback gate. CocoaPods installed the periodic-timeline patch, but the Release simulator compile failed in pinned SwiftAudioEx 0.14.7 at `AVPlayerWrapper.swift:227`: the cache reset inserted immediately before `self.avPlayer.replaceCurrentItem(with: currentItem)` is inside `DispatchQueue.main.async`, and Swift requires the helper call to use explicit `self`. The exact compiler diagnostic is `call to method 'lxSetCachedCurrentTime' in closure requires explicit use of 'self' to make capture semantics explicit`.

The correction changes only that generated call to `self.lxSetCachedCurrentTime(0)` and strengthens the source regression to require the explicit-self form and reject the previous form. The position source, lock, seek/reset semantics and the unchanged 3000 ms playback gate are otherwise untouched. Local cross-checks against the exact Run82 source artifact pass the position-cache source contract, all nine TrackPlayer timing contracts, all nine smoke-driver failure tests and Podfile Ruby syntax. Simulator compilation and native playback remain gated by the next Actions run and are not predeclared successful here.

## Run83: remote path passed; cached MP3 handoff still terminated the app

Run83 (`d7073a24205ba2adf5cb454b288bc19476e5b2be`) compiled and advanced beyond the earlier cold-remote blocker. The MP3 remote stream, volume, pause/resume and complete RNFS cache publication all passed, and the required 54-view UI evidence was complete. The first failure moved to `mp3: local cache playback and seek`: the first cached-file position read returned, the next probe remained pending, and the simulator process had already exited when `/usr/bin/sample` attempted to inspect it. No crash stack was retained, so this report does not label the termination as a proven AVFoundation or Swift crash.

The same failure point is independently present in Run74 (`e1314ec444fdfd0233e8da9a3dc8203412a33c04`), and its `trackPlayerCore.ts`, `resourceLoader.ts`, cache adapter and local-playback test are byte-for-byte equivalent to Run83 for this handoff. That excludes the later periodic-position cache as the origin of the cached-file termination.

Source review found a deterministic iOS queue-transition hazard in the unchanged handoff. The old implementation appended the replacement track, jumped to it, then asynchronously removed every previous queue entry. SwiftAudioEx 0.14.7 decrements `currentIndex` before removing a preceding item, which emits another queue-index callback while the replacement AVPlayerItem is loading. RNTrackPlayer turns that mutation into another `playback-track-changed` event. This ordering is confirmed by the pinned dependency source; the missing crash report means it is not claimed as the captured termination stack.

The iOS replacement path now keeps a single-item queue: when a current TrackPlayer item exists it awaits `reset`, clears the mirrored JS queue, adds the new source, avoids a redundant same-index skip, then starts/pauses and performs only a nonzero seek. Android retains the previous append/skip/compact behavior. The cache playback lease still remains valid until the replacement has opened and `adoptAudioCacheURL` releases the old lease.

Cross-checks before commit: Build79 now executes remote-to-local replacement and requires one reset, one resulting cached-file queue item, no asynchronous remove and no redundant skip; all 11 Build79 groups pass. TrackPlayer timing-contract checks (9), periodic-position source contract, smoke-driver failure attribution (9), Build86, Build82, Build81, audio-cache behavioral checks (20), sync/catalog races (6) and Podfile Ruby syntax also pass in the downloaded Run83 source snapshot. Native simulator playback, FLAC, repeated remote/cache transitions, offline restart, Archive and IPA remain release gates and are not predeclared successful here.
